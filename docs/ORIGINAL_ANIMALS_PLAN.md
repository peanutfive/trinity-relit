# M5 动物、鸟笼与壁橱谜题开发计划

2026-10-20。基线为 M4 开发提交 `14ccebc`，研究预备登记 T22；运行时登记 T23，分支 `codex/animal-mechanics`。
本计划已完成首批原版证据和影响核对；人类已明确授权完整 M5 运行时范围，登记 T23。按下面阶段连续实施，
不再为每个动物或每处接线重复请求确认。只在开发分支提交，不合并 main、不部署。

## 1. 交付目标

玩家能够从正常新游戏取得小屋鸟笼、发现并捕获旅鼠、在正确剧情阶段捕获走鹃，
经历拿取、装笼、关笼、开笼、逃逸、入水及尸体回收。相关状态必须可保存、刷新和导入。
闭门放旅鼠与响尾蛇解法作为有独立证据门槛的后续阶段，连同威胁、回避和死亡时序一起完成，
不能只播放一段“蛇吃旅鼠”文字就算完成谜题。

保留全部现有房间 ID，包括 Ranch 的 27 间；不调整 Desert 进入 Ranch 的入口或其他跨章地图。
本批仅增加动物所需的跨章状态衔接，不恢复旧 embedding 启动路径，不改模型加载或 UI 布局。

### 2.3 行为及需要保持的区别

| 行为 | 原版结论 | 实施要求 |
|---|---|---|
| 小屋取得鸟笼 | 关闭的笼内已有喜鹊；笼首次取得 +1 | 补正常取得路径；不能初始化成空笼或重复加分 |
| 手拿旅鼠 | 同动作后先挣扎，下一有效回合仍手持则逃逸 | 保存持有窗口；未知输入和免推进动作不推进窗口 |
| 装入旅鼠 | 活旅鼠绕过普通笼内 size 限制；首次装笼 +1 | 奖励按笼的首次状态保护，不能按每次 put 加分 |
| 手拿 / 装入走鹃 | 有啄手和扑腾阶段，装笼重置窗口，允许下一步关笼 | 专属状态机；不能 put 后永远留在敞开的笼内 |
| 亮处开喜鹊笼 | 一般立即飞走；封闭小屋、壁橱和保护膜另有分支 | 不能统一 destroy；所走分支须有原版响应与证据 |
| 开旅鼠笼 | 开笼动作可立即调用旅鼠回调，之后还有普通回合结算 | 验证立即调用与普通 tick，避免漏调用或多调用 |
| 普通岸边释放旅鼠 | 跑出视野；悬崖会跳下，平台会坠水 | 逃逸按场景区分；平台生成水底 DLEM，与笼整体溺水分开 |
| 普通入水 / 下潜 | 只在笼直接由 PLAYER 持有时执行笼内溺水替换 | 不借通用递归可见性扩大到任意深层笼 |
| 风车坍塌 | 笼直接在 PLAYER 或 IN-MILL 均替换；另独立处理直接持有 / 平台上的 MEEP | 不能统一成“所有携带动物都淹死” |
| 笼内溺水 | 三个独立分支替换活体，撤销其回调，尸体仍在笼内；无输出、无计分 | 不误杀玩家；不重复制造尸体或恢复活体 |
| 尸体回收 | 闭笼可见不可取；开笼后可取回查看 | 三种均有实际回收证据；尸体不会因开笼逃跑 |
| 尸体重新装笼 | 死旅鼠、死喜鹊可装；死走鹃因 size 5 被拒绝 | 活走鹃专例不能错误用于死走鹃 |
| 蛇吃旅鼠 | 移除旅鼠及蛇、首次 +3；不留下可捡尸体 | 和门、光照、威胁及回合顺序一起验证 |

## 3. 当前实现的具体缺口

1. `cage.start` 为空，小屋“查看鸟笼”仍是旧占位事件，正常通关没有取得笼子的路径。
2. 旅鼠仍混用 `itemLoc="cage"`、`cage_has_lemming` 和死亡 flag；没有独立喜鹊、走鹃及尸体对象。
3. Tundra 当前过早放置单只旅鼠，拿取后没有逃逸窗口；两个章节事件复制装笼逻辑。
4. 走鹃在原版先由 `MEEP-TO-ZERO` 准备到塔底，再由 `AT-ZERO-F` 首次进入激活。
   `base_of_tower` 已核对为 #146，当前没有该动物进入接点；仅增加物品定义无法正常捕获。
5. Ranch 旧事件开笼不更新通用 `cage_open`，开门后把所谓“死亡旅鼠”仍放在 Assembly，
   没有正确撤销动物状态、移除蛇和首次 +3。
6. Assembly / Closet 的门状态、局部光照、蛇威胁缺少完整执行链；加入一段致死倒计时会改变
   当前通关路线，必须同时验证生存解法，不能杜撰绷带或刀能解毒。
7. 现有全流程测试明确跳过了鸟笼取得，拿旅鼠后长期徒手携带；M5 后必须走真实捕获路线，
   不能以测试注入物品 / flag 或放宽窗口来维持旧结果。
8. `bird`、`鸟` 和动物名称会在活体、尸体及场景对象之间歧义；精确输入与语义候选都须按可见实体消歧。

## 4. 状态、执行与旧档契约

### 4.1 唯一位置与动物阶段

- 沿用 M4 `itemLoc` 及 `in:<id>`；`contents()` 为直接内容，`has()` 仍为直接手持。
  新增动物规则不得绕过 `isVisible()`、`isAccessible()` 或容器循环保护。
- 裂缝可采用明确的父对象表示，或保留房间位置加已发现阶段；二者必须选定唯一真相，
  拿取、描述、候选和读档共用，不能同时在裂缝和地面出现一只旅鼠。
- 物种、活体 / 尸体、死亡原因、持有 / 笼内窗口、激活 / 撤销状态分别表达。
  阶段保存在可校验的纯状态中，不把闭包写进存档，不占用唯一 `state.timer`。
- 动物规则集中于新 `animal-rules.js`，不依赖章节是否仍加载；章节只提供真实进入、物件及水库接点。
- 完成命令后，立即动作与普通 `_postTurn()` 的执行顺序按原版探测表实现。
  WAIT 的每一有效步各执行一次；未知输入、取消、语义未确认和 `advancesTurn:false` 不运行普通动物 tick。
- 动物退出 / 死亡及时撤销其状态；装笼、放笼、切章、恢复均不能无意重置窗口。
  与平台 / 呼吸同时存在时补顺序对照，不能默认动物一定最先或最后。

### 4.2 走鹃跨章衔接

选择在 `islet.js` 两条成功进入 Desert 的路径调用共享准备逻辑，
`desert.js` 的 `base_of_tower.onEnter` 只消费已准备的首次相遇状态。
转章失败不准备动物；续玩 / 导入不重放 onEnter；重复进章、明确移走或已死亡的走鹃不复活。
准备态、可拿状态及与 ruby / box 的衔接须对照原版单独检查，不能挪动房间或入口来绕过依赖。

### 4.3 存档 v3（已实现）

M4 v2 已有真实容器，但旧 `"cage"` 位置与动物死亡 flag 尚未迁移。
M5 改变了这些字段的含义，采用明确版本迁移，避免旧保存与新游戏初始化混淆。

| 旧状态 | 迁移规则 |
|---|---|
| 明确 `itemLoc.lemming="cage"` 且仍活着 | 转 `in:cage`，移除旧笼内 flag；不再维护双重真相 |
| 笼内 flag 与明确 destroyed / 其他位置冲突 | 明确物品位置优先；不得复制第二只或自动塞回笼 |
| 旧 `lemming_dead` / 蛇吃标志 | 不恢复活体；蛇吃历史不生成尸体，不补发分数 |
| 已有首次旅鼠装笼得分标志 | 映射奖励已领取，drop / retake / reinsert 不再加分 |
| 旧档已持有鸟笼、但没有首次取得得分字段 | 标记历史处理，不追补 +1 或允许刷分 |
| 旧档没有新增动物字段 | 按有证据的历史阶段保守迁移；不能套用新游戏 start 补出喜鹊 / 走鹃 |
| 无法可靠映射的矛盾状态 | 拒绝或明确保留不可推断状态并说明边界，不能猜测死亡原因 / 落点 |

- `prepareSave()` 先在独立状态迁移、校验关系和阶段，再一次性替换活状态。
- 浏览器读取顺序为 v3 → v2 → v1，只有高版本键不存在才回退；坏 v3 不得静默读取旧进度。
- 成功升级写 v3 并保留旧键；明确重开先清旧键再清当前键，任何失败都不得 reload 丢失保护。
- 导入 v1 / v2 / v3 一律先预检、再确认、再写规范化 v3；坏档 / 取消不改原键，加载失败继续保护自动保存。
- v3 必须拒绝非法阶段、非法父项、自包含 / 循环、活体与其尸体同时被错误初始化等无效数据。
  合法历史中两个对象都已显式出现的情况先判断来源，不能靠通用“只准一个对象”误删物品。

### 必须包含的自动与浏览器用例

- 初始笼关闭且有喜鹊、首取 +1、重复拿放不加分；封闭 / 开门小屋的开笼区别。
- 裂缝发现一次；取旅鼠 → 装笼 → 关笼正常成功；等待 / 移动导致逃逸，未知输入不影响窗口。
- 走鹃准备、塔底首次相遇和可拿状态只发生一次；失败切章、刷新、导入不会生成或重放。
- 活旅鼠 / 走鹃装笼特例；死走鹃恢复普通尺寸限制；闭笼活体 / 尸体可见但不可取。
- 三种活体入水变为对应溺尸；重复入水不重复替换；开笼、取尸、查看原因和再次放置正确。
- 普通入水只处理直接持笼；平台笼坍塌处理正确；不把容器递归或源例程三个 if 当作全组合证明。
- 平台开笼旅鼠先坠水，再独立平台坍塌；取镜免推进和气息回调没有多跑一次。
- 每个持有 / 笼内窗口中途保存恢复，动物退出后不再触发回调；WAIT 每步一致。
- v1 / v2 / v3 本地键与导入、损坏当前键、升级写失败、重开删除失败、取消导入保护。
- 可见活体 / 尸体同别名有歧义时澄清；语义候选过期后不误抓另一只或凭空执行。
- 蛇警告、安全撤退 / 关门、旅鼠解决、咬伤后果各有独立用例；首次 +3 不能重刷。
- 至少一条不注入物品 / flag 的端到端新游戏捕获路线；图可达测试不得当作带危险状态的解谜测试。
- develop-web-game 标准客户端与专项真实页面输入；逐个检查双语输出、截图及 JS 错误。
